# Consultant view of client assessment status

**Held for an owner decision.** A consultant can select a client, open Cyber Security and read that client’s entitled assessment list on the paid stack. A page showing several clients’ NIST CSF or ISO 27001 readiness self-assessment statuses needs an additional cross-client read. Until that decision, use the organisation chooser and open each client deliberately. [Current 375px chooser (fictional accounts)](../../.github/pr-evidence/n4/consultant-chooser-375.png)

## Decision for the owner

May the server disclose one status for each currently entitled NIST or ISO profile on an activated client of the signed-in consultant, without switching the selected organisation? Approval would authorise a **status-only portfolio operation**. Opening an assessment would still require deliberate client selection and the ordinary selected-client read. Existing subject-scoped starter tables, the current binding, membership and entitlement records, and the paid revisions in migration 0030 contain the necessary facts for activated starter clients. Other relationships stay outside this proposal until there is equivalent evidence. The missing authority is in the application. The proposal needs no new table, stored status, database role, grant or RLS policy. [Starter scope and subject policies](https://github.com/Discla1mer/nofries-platform/blob/a29ef1faec046cdca65ad99bf80dfeb217257e43/database/migrations/0011_starter_signup.sql#L13) · [Paid revision keys and RLS](https://github.com/Discla1mer/nofries-platform/blob/942ea196c1bbfe8151ea0ad7971eff60cfee45ba/database/migrations/0030_paid_assessment_revisions.sql#L3)

## Proposed read

Use one same-origin `GET /api/dashboard/organisations/paid-framework-status` for the visible **Organisations** page. Require the current customer session and `x-nofries-dashboard-generation`. Accept only the optional canonical `afterBindingId` UUID used by the existing chooser, as a position in the subject’s directory. In this proposed view request ten bindings from the ordinary directory and use the same cursor and order for the status read. The existing chooser normally requests fifty. The chooser supplies names and its own next cursor. The server chooses the targets and the two published pins. A caller cannot supply a subject, tenant, target organisation, framework or version.

A successful response has exactly `{rows: [{bindingId, moduleId, profileId, version, status}]}`. Return at most twenty rows, in binding order then profile ID order. Both pins use `cyber_security`. They are `nf-nist-csf-2-0-core/2026-09-08.1` and `nf-iso-27001-2022-readiness/2026-11-19.1`. The UI joins only to binding IDs still visible on that page and generation. No labels need duplicating. Keep assessment IDs, answers, dates, scores, publications, plan details, totals and entitlement diagnostics out of the response.

1. Gate route discovery on `NOFRIES_PAID_FRAMEWORKS_ENABLED` exactly `true`. Otherwise return the ordinary 404 before reading the directory. Require an approved customer binding with account type `consultant`, a live session, the expected generation and the existing instance and restore checks. Deny other callers without client data. Use the existing subject-restricted directory solely to identify candidates. Any paid UI asset requires the existing entitlement gate. Keep it out of the free bundle.
2. For each candidate, use the normal tenant-and-organisation scoped transaction. Require an activated `dashboard_starter_accounts` consultant account for the captured subject. Match its `account_id` to an activated, undiscarded `dashboard_starter_scopes` row with `ordinal > 0` and matching subject, account type, binding ID, admission authority ID, tenant and organisation. Ordinal zero is the home workspace. Check the live binding, admission, active membership, `assessment.read`, current product and exact module/profile/version grant using the paid reader’s evaluator. Subject-reader and runtime queries keep their existing roles and scope. Missing client proof, inactive or free clients, and unentitled tuples contribute no row. A setup label, plan or earlier grant cannot establish eligibility. [Client discriminator](https://github.com/Discla1mer/nofries-platform/blob/a29ef1faec046cdca65ad99bf80dfeb217257e43/database/migrations/0019_starter_client_discard.sql#L44) · [Exact paid access](https://github.com/Discla1mer/nofries-platform/blob/942ea196c1bbfe8151ea0ad7971eff60cfee45ba/api/shared/assessmentLifecycle/paidAssessments.js#L79)
3. For each authorised tuple, query `dashboard_framework_revisions` under its existing scoped RLS, with bound tenant, organisation, profile ID and version. Take the greatest revision per assessment ID. In SQL, inspect only each head’s status and update time plus its internal ID for tie-breaking. Reduce all heads to one status within that transaction. Older revisions and the selected-client list’s 25-row page cannot determine a status. A single aggregate must both detect invalid heads and select a winner before returning its one scalar. Apply existing request and query budgets. An exceeded budget means the read is unavailable. [Current list projection](https://github.com/Discla1mer/nofries-platform/blob/942ea196c1bbfe8151ea0ad7971eff60cfee45ba/api/shared/assessmentLifecycle/paidAssessments.js#L158)
4. Buffer the page. Before release, recheck the original session, generation, client relationship and exact paid authority for **every contributing binding and tuple**, including an empty assessment history. Use the portfolio’s existing deterministic lock order. Keep its through-commit and response-time checks, with the paid scope and tuple captured for each row. A changed decision discards the whole page. Reuse the scoped assessment-read audit without recording answer content. Serve responses with `Cache-Control: private, no-store`. Clear prior rows on navigation, generation change, denial or failure. This operation never changes selection, assessment records, grants or usage. [Existing portfolio disclosure pattern](https://github.com/Discla1mer/nofries-platform/blob/942ea196c1bbfe8151ea0ad7971eff60cfee45ba/api/shared/database/dashboardRequestDatabase.js#L1433)

| Wire status | Display | Rule over current heads for one authorised tuple |
| --- | --- | --- |
| `not_started` | Not started | The complete query succeeds and finds zero heads. |
| `in_progress` | In progress | At least one head is `created` or `in-progress`. An open attempt takes precedence even over a newer submission. |
| `submitted` | Submitted | There is at least one head and all heads are `submitted`. |

Within the winning group choose the latest `state.updatedAt` instant, then the lowest assessment ID in byte order on a tie. Revisions are ordered only within an assessment. An unknown status, malformed head, incomplete query, missing required publication or storage failure returns one generic 503 for the page, with no rows. Show “Assessment status unavailable”. A session or authority loss during assembly returns a generic 403 with no rows. A successful empty page simply adds no paid labels. The UI displays “Not started” only for an explicit `not_started` row.

## Review and release order

Review this design independently on main. Before any implementation, obtain the owner’s explicit decision on the cross-client disclosure and independent review of the relationship proof, paid scope, query projection and final disclosure check. A future runtime change depends on #502 and #507, and on #506 for the ISO publication. Keep coordinated activation separate.

On disposable loopback PostgreSQL, exercise both pins, two consultants, home and pending/discarded clients, free and mixed entitlements, wrong versions, and same organisation IDs across different tenants wherever the fixture permits. Verify zero, created, saved and submitted histories, a newest revision replacing an old open one, open plus newer submitted attempts, tied times, more than 25 heads, malformed data and budget failure. Check the exact response fields and the absence of counts or partial results. Race binding or entitlement revocation, session expiry and generation changes between clients and through final disclosure. Confirm ordinary NCSC access, score, usage, grants and selection are unchanged. In the browser check keyboard/375px operation, clearing stale rows, and absence of paid assets with the flag off. These are acceptance tests for a future implementation. The linked screenshot records only the existing chooser.
